# Chapter 2: Literature Review

## 2.1 Approach to the Review

Literature was identified by systematically searching arXiv, ACM Digital Library, IEEE Xplore, and ScienceDirect for work published primarily between 2024 and 2026 on four themes directly relevant to the proposed system: (i) LLM- and RAG-based vulnerability detection, (ii) reduction of false positives by combining LLMs with static analysis, (iii) automated severity/CVSS scoring, and (iv) automated vulnerability repair and secure code generation. Twenty papers were selected for detailed review, spanning peer-reviewed venues (ACM TOSEM, ACM Computing Surveys, EMNLP, ACL, Springer Cybersecurity/IJIS) and recent arXiv preprints. This selection deliberately favours recent (2024–2026) work so the review reflects the current state of the art rather than earlier deep-learning-only vulnerability detection methods (e.g., graph neural network or LSTM-based detectors), which are referenced only for historical contrast.

## 2.2 LLM- and RAG-Based Vulnerability Detection

**[L1] Vul-RAG: Enhancing LLM-based Vulnerability Detection via Knowledge-level RAG** (Zhang et al., ACM TOSEM 2025; arXiv:2406.11147). This is the most directly relevant prior work. The authors show that plain LLMs achieve only 0.06–0.14 pair-wise accuracy when asked to distinguish vulnerable code from its patched version on the 586-pair PairVul benchmark (Linux kernel CVEs, Top-10 CWEs) — evidence that LLMs default to superficial pattern matching rather than reasoning about root cause. Vul-RAG extracts multi-dimensional vulnerability knowledge (functional semantics, cause, fix) from historical CVEs, retrieves the most relevant knowledge via BM25 similarity, and asks the LLM to reason about whether the *cause* is present without the corresponding *fix*. This lifts pair accuracy by 16–24% and balanced precision by 9–14% over baselines, and a user study shows retrieved knowledge raises manual reviewer accuracy from 60% to 77%. The system found 10 previously unknown Linux kernel bugs, 6 of which were confirmed with assigned CVEs. **Relevance:** this validates the core architectural bet of the proposed system — that grounding retrieval in structured, cause-and-fix-level knowledge (rather than raw code similarity alone) is what drives accuracy gains, directly motivating our OWASP/CWE knowledge base design (Chapter 3).

**[L2] RepoAudit** (PurCL, GitHub project, 2025). An autonomous multi-agent LLM system for repository-level code auditing across C/C++, Java, Python, and Go using tree-sitter parsing rather than full compilation. A MetaScanAgent performs syntactic analysis and a DFBScanAgent performs inter-procedural data-flow analysis to catch cross-function/cross-file bugs (e.g., null-pointer dereference, memory leaks) framed as source-must/must-not-reach-sink problems. Reports over 100 confirmed, fixed bugs in open-source projects in a single quarter. **Relevance:** demonstrates the practicality of repository-level (not just function-level) analysis, which is central to our GitHub-repository ingestion design, and validates a multi-agent decomposition of the analysis pipeline.

**[L3] VulnGym: Benchmarking Coding Agents for Repository-Level Vulnerability Detection** (arXiv:2608.02001, 2026). Introduces a benchmark specifically for evaluating agentic, repository-scale vulnerability detection rather than isolated function snippets, closer to real-world usage. **Relevance:** informs our own evaluation plan for repository-scale (not just per-file) detection accuracy.

**[L4] A Sequential Multi-Stage Approach for Code Vulnerability Detection** (EMNLP 2025). Proposes breaking vulnerability detection into sequential stages (e.g., candidate localisation followed by fine-grained classification) rather than a single end-to-end LLM call. **Relevance:** supports our design decision to separate retrieval, detection, and severity scoring into distinct pipeline stages rather than one monolithic prompt.

**[L5] LLMs in Code Vulnerability Analysis: A Proof of Concept** (arXiv:2601.08691, 2026). A practitioner-oriented proof-of-concept evaluating off-the-shelf LLMs directly on vulnerability analysis tasks, without a retrieval or knowledge-grounding layer. **Relevance:** used as a "naive LLM baseline" comparator against which the value of our RAG + knowledge-base grounding can be argued.

**[L6] A Systematic Literature Review on Detecting Software Vulnerabilities with Large Language Models** (arXiv:2507.22659, 2025). A large-scale SLR covering 227 studies (Jan 2020–Jun 2025; 46.7% from 2024 alone), taxonomising approaches by detection task (binary/multi-class/vulnerability-specific classification), input representation (raw code, AST/CFG/graph-structured, prompt-engineered), and architecture (LLM-centric vs. hybrid). It identifies seven recurring gaps: fragmented datasets, label-quality/class-imbalance issues, inconsistent evaluation metrics, poor coverage of emerging vulnerability types, weak semantic representation of subtle code differences, low interpretability, and limited real-world deployment integration. **Relevance:** several of these gaps (interpretability, standards-grounding, deployment integration) are exactly what the proposed system targets — the OWASP/CWE-grounded explanations address interpretability, and the dashboard targets deployment usability.

**[L7] LLMs in Software Security: A Survey of Vulnerability Detection Techniques and Insights** (ACM Computing Surveys, 2025). A broad survey covering prompting strategies, fine-tuning, and hybrid neuro-symbolic techniques for LLM-based security analysis, with a discussion of open challenges around trust and evaluation rigor. **Relevance:** corroborates the general shift from purely deep-learning classifiers toward LLM-based, explanation-capable detectors.

**[L8] Source code vulnerability detection based on deep learning: a review** (Springer *Cybersecurity*, 2025). Reviews the pre-LLM generation of deep-learning vulnerability detectors (graph neural networks, sequence models) and their limitations — chiefly, poor generalisation across projects and lack of explainability. **Relevance:** used as historical baseline/contrast to justify why an LLM+RAG approach is proposed instead of a purely learned classifier.

## 2.3 Reducing False Positives via LLM–Static-Analysis Integration

**[L9] ZeroFalse: Improving Precision in Static Analysis with LLMs** (arXiv:2510.02534, 2025). Proposes a five-stage pipeline — canonicalising CodeQL/SARIF alerts, contextual enrichment with dataflow-sensitive annotations, CWE-specific prompt micro-rubrics, precise code-path reconstruction, and LLM adjudication — to filter static-analyzer false positives. On the OWASP Java Benchmark (1,974 cases, 10 CWEs) the best models (Grok-4, Gemini 2.5 Pro) reach F1 ≈ 0.91; on real-world OpenVuln data, GPT-5 reaches F1 = 0.955 (precision = 1.0). Reasoning-oriented models and CWE-specialised prompting outperform generic prompting. **Relevance:** directly informs our severity/detection module's prompt design — using CWE-specific rubrics rather than a single generic prompt is adopted as a design principle in Chapter 3.

**[L10] Reducing False Positives in Static Bug Detection with LLMs: An Empirical Study in Industry** (Tencent; arXiv:2601.18844, 2026). A large industrial study on Tencent's BkCheck static analyzer across three bug classes (null-pointer dereference, divide-by-zero, out-of-bounds) with 433 double-reviewed alarms, of which 76%+ (effectively >90% accounting for incomplete records) were false positives, costing developers 10–20 minutes of manual review each. Hybrid LLM + static-analysis techniques (LLM4PFA) reach 0.93–0.94 accuracy and eliminate 94–98% of false positives, at $0.0011–$0.12 per alarm — far cheaper than manual review — though the models still struggle with long code contexts and complex cascaded constraints. **Relevance:** the strongest empirical justification in the reviewed literature for the project's central hypothesis — that LLM+context (rather than static rules or LLMs alone) is what reduces false positives at acceptable cost; this evidence is used directly in Chapter 1's motivation and in Chapter 3's cost/feasibility analysis.

**[L11] Large Language Models Versus Static Code Analysis Tools: A Systematic Benchmark for Vulnerability Detection** (arXiv:2508.04448, 2025). Head-to-head evaluation on 10 real-world C# projects (63 embedded vulnerabilities) comparing SonarQube/CodeQL/Snyk against GPT-4.1/Mistral Large/DeepSeek V3. LLMs achieve substantially higher F1 (0.75–0.80) than static tools (0.26–0.55) with better recall, but worse line/column localisation precision due to tokenisation artefacts. The authors explicitly recommend a **hybrid** workflow: LLMs for broad early triage, deterministic scanners for high-assurance verification. **Relevance:** directly supports our design of retrieving *intra-repository* code context (not just isolated snippets) to improve LLM localisation, and motivates keeping a rule-based severity layer rather than trusting LLM judgment end-to-end.

**[L12] Towards Effective Complementary Security Analysis using Large Language Models** (arXiv:2506.16899, 2025). Studies LLMs as a complementary layer *on top of* existing static analysis pipelines rather than a replacement, focused on triaging analyzer output. **Relevance:** reinforces the "LLM as adjudicator over structured analyzer output" pattern used in our detection module.

**[L13] LLM-Driven Adaptive Source–Sink Identification and False-Positive Mitigation for Static Analysis** (ACM ICCIA 2025). Uses LLMs to adaptively identify taint sources/sinks (rather than relying on a fixed rule list) and to mitigate resulting false positives. **Relevance:** relevant to designing the repository-context retrieval step, since accurate source/sink identification depends on cross-file context similar to what our vector-retrieval-over-the-repository step is designed to supply.

## 2.4 Automated Severity / CVSS Scoring

**[L14] AutoCVSS: Assessing the Performance of LLMs for CVSS Scoring** (EMNLP 2025 Industry Track). Evaluates GPT-4o, o3-mini, LLaMA3, and DeepSeek-R1 on predicting individual CVSS metrics as classification tasks, using >27,000 NVD CVE records (2023–2024) under three regimes: abundant data, low-resource (2.1k samples), and the CVSS v4.0 transition (38 labelled samples, essentially zero-shot). Key finding: with abundant labelled data, fine-tuned supervised baselines (CVEDrill, ModernBERT) beat LLMs; but under low-resource or new-standard conditions, LLMs become competitive and outperform conservative baselines by up to 33 percentage points — a hybrid supervised+LLM approach wins on half the metrics overall. Notes that the *median manual CVSS-scoring delay grew from 2.7 days (2019) to 8.2 days (2023)*. **Relevance:** this is the strongest direct precedent for our severity-scoring module, and its finding — that pure-LLM severity scoring is not reliably better than rule-based scoring, especially with limited grounding — is the direct justification for the project's decision to use a **custom, CVSS-inspired rule-based scorer** rather than relying on raw LLM severity judgments (see Chapter 3, Innovation).

**[L15] Automatic CVSS-Based Vulnerability Prioritization and Response with Context Information and Machine Learning** (MDPI *Applied Sciences*, 2025). Combines organisational/contextual signals (asset criticality, exposure) with ML-predicted CVSS components for prioritisation, going beyond a context-free severity number. **Relevance:** informs a possible future-work extension — incorporating repository/project context (e.g., whether a flagged function is reachable from an entry point) into severity weighting.

**[L16] AI-enabled automated common vulnerability scoring from CVE descriptions** (Springer *International Journal of Information Security*, 2024). Predicts CVSS scores directly from free-text CVE descriptions using NLP models, a precursor line of work to the LLM-based approaches above. **Relevance:** baseline evidence that natural-language-grounded severity prediction is feasible, supporting the design choice to derive severity partly from the LLM's structured vulnerability explanation rather than only from CWE-ID lookup tables.

## 2.5 Automated Repair and Secure Code Generation

**[L17] A Case Study of LLM for Automated Vulnerability Repair: Assessing Impact of Reasoning and Patch-Validation Feedback** (ACM AIware 2024). Shows that giving the LLM explicit reasoning steps and iterative patch-validation feedback (e.g., re-running tests/analyzers on a proposed patch) substantially improves repair quality over single-shot patch generation. **Relevance:** informs the design of our remediation-suggestion module — a single LLM call producing a "fix" is treated as a first draft, with the before/after comparison presented for *developer* validation rather than auto-applied.

**[L18] Enhanced automated code vulnerability repair using large language models** (Elsevier *Engineering Applications of AI*, 2024). Proposes techniques to improve the correctness and minimality of LLM-generated security patches. **Relevance:** supports the "before-and-after code comparison" feature — minimal, explainable diffs are preferred over large rewrites.

**[L19] Generating vulnerability security fixes with Code Language Models** (Elsevier *Information and Software Technology*, 2025). Benchmarks code-specialised LLMs (as opposed to general-purpose LLMs) specifically for generating security fixes, finding code-specialised models produce more compilable/correct patches. **Relevance:** informs model-selection guidance in Chapter 3 (preferring code-tuned LLMs/embedding models for the remediation-generation sub-task).

## 2.6 Benchmarks and Evaluation Resources

**[L20] SecVulEval: Benchmarking LLMs for Real-World C/C++ Vulnerability Detection** (2025) and **VulDetectBench: Evaluating the Deep Capability of Vulnerability Detection with Large Language Models** (arXiv:2406.07595, 2024) together establish that current LLM vulnerability detectors perform well on simple existence/type-classification tasks but degrade sharply on deeper tasks such as identifying the precise vulnerable statement or the correct patch — i.e., detection ability does not imply localisation or repair ability. **Relevance:** justifies evaluating the proposed system at multiple granularities (chunk-level flag, line-level localisation, and fix quality) rather than a single detection-accuracy number, and tempers claims about remediation-suggestion reliability (developer review is kept in the loop).

## 2.7 Comparative Summary

| # | Work | Core Technique | Grounding Source | Reported Strength | Reported Limitation |
|---|------|----------------|-------------------|--------------------|----------------------|
| L1 | Vul-RAG (TOSEM 2025) | Knowledge-level RAG | Historical CVE knowledge (cause+fix) | +16–24% pair accuracy; found real 0-day-class bugs | Fails on truly novel patterns not in the knowledge base |
| L2 | RepoAudit | Multi-agent, dataflow analysis | Tree-sitter parsing, no LLM knowledge grounding | Repo-scale, cross-file bug detection | No standards-grounded (OWASP/CWE) explanation layer |
| L6 | SLR (227 studies) | Taxonomy/meta-analysis | N/A | Maps the whole field, exposes 7 gaps | Confirms lack of standardised, interpretable, deployable systems |
| L9 | ZeroFalse | LLM adjudication over SAST alerts | CodeQL/SARIF + CWE micro-rubrics | F1 up to 0.96 on real-world data | Depends on quality of upstream static-analyzer alerts |
| L10 | Tencent industry study | Hybrid LLM+static (LLM4PFA) | Enterprise static analyzer context | 94–98% FP elimination, very low cost/alarm | Weak on long context, complex constraints |
| L11 | LLM vs SAST benchmark | Head-to-head comparison | None (pure LLM vs pure static) | LLMs: F1 0.75–0.80 vs static 0.26–0.55 | LLM line/column localisation is imprecise |
| L14 | AutoCVSS | LLM CVSS prediction | NVD CVE corpus, few-shot RAG | Strong in low-resource/new-standard settings | Loses to supervised models when data is abundant |
| L17 | LLM repair case study | Reasoning + patch-validation feedback | Test/analyzer re-execution | Iterative feedback improves patch quality | Single-shot patches are unreliable without validation |

**Positioning of the proposed work.** No single reviewed system combines all of: (a) repository-scale ingestion and chunking (as in L2/L3), (b) RAG grounded specifically in *externally curated, standards-based* knowledge — OWASP Top 10 and CWE — rather than only historical CVE pairs (as in L1) or raw static-analyzer output (as in L9/L10), (c) a transparent, rule-based CVSS-inspired severity layer that does not rely solely on LLM judgment (motivated directly by L14's finding that pure-LLM scoring is not reliably superior), and (d) a developer-facing dashboard presenting an explainable, standards-referenced, before/after-verifiable finding. This combination — RAG over dual knowledge sources (own-repository context *and* an external security standards corpus), paired with a deterministic severity layer — is the specific gap the proposed system targets, and is elaborated in Chapter 3.
